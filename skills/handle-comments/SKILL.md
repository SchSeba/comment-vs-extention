# Handle Local Review comments

1. Find the absolute Git worktree root with `git rev-parse --show-toplevel`. If the user specifies a worktree, use that worktree. If the target is ambiguous, ask which worktree they mean.
2. On the first handling round for this review in the current chat, read the checkout’s README to understand what the project does, how it is used and tested. Read the applicable `AGENTS.md` files and any coding, reviewing, and validation guidance in `.ai-rules/`. Identify the project by its canonical Git remote's repository name, or the worktree name if there is no remote. In an available [ai-plugins](https://github.com/SchSeba/ai-plugins) checkout, or a temporary clone of that repository, read the project's `CODING.md`, `REVIEWING.md`, and `VALIDATION.md` under `projects/<project>/` when present. Apply those conventions and checks, giving the review checkout's own instructions precedence. If shared guidance is unavailable, report that and use the checkout's guidance.
3. On that first round, before fetching comments, inspect the full relevant Git diff. Establish the comparison from the review request or chat. For a branch or PR inspect the committed patch from the merge base of the target and review head to the review head, or use the explicit commit range. If different plausible bases give different changes, clarify the comparison. For a local Source Control review start with the uncommitted changes. Check `git status --short --untracked-files=all`, read both `git diff --cached` and `git diff`, and inspect relevant untracked files. Include changed paths without comments. Read applicable directory-level instructions and trace the affected entry points, callers and tests independently of comment excerpts.
4. Write a short account in chat for the reviewer before acting on feedback. Identify the comparison, the feature or bug, why the change is needed, the approach, the before-and-after flow, and what the tests cover. Label inferred intent. Ask a specific question if an unresolved decision would change the behavior or fix, and wait before acting on that decision. Continue when intent is clear. On later rounds in this chat, reuse the account for the same review, check the current range, patches, instructions and reviewer decisions, and update it with material changes. Rebuild the context when the review changes or the earlier account is unavailable.
5. Call the `local-review` MCP server's `list_pending_comments` tool with that root as `repository` and the `scope` from the user's prompt if provided. If the tool is unavailable, tell the user to check `/mcp` and resume their session after configuring the server. If the result is empty, report that there are no pending comments on the current branch.
6. Keep each pending ID and pass its `scope` and worktree root to every subsequent call. Stop if the checkout or branch changes. For each ID, call `get_comment_context` and read the current feedback and its `history` of earlier feedback and replies in thread order, including decisions that later feedback revised. Read the directory-specific `AGENTS.md` files that apply to the affected paths. Find the repository's required validation commands in its guidance, contributor docs, or build tasks.
7. Investigate the reviewer's premise against the current diff and working tree. Trace relevant callers, data and tests, and check dependency claims against the pinned version. For a question, answer from that evidence. For a requested change, identify the expected behavior, plan the fix and an edge case that could disprove it. Compare viable options when the reviewer asks for a design choice. If a comment asks for both an explanation and a change, cover both.
8. Work through comments on the same file in listed order. Refresh `get_comment_context` immediately before editing, even after another fix in that file. Compare the saved excerpt and nearby lines with the current file. Independently verify changed or uncertain locations. Implement the requested outcome and preserve existing edits. If it is already satisfied, or the suggestion would break a caller, identify the specific evidence.
9. Run focused tests for changed behavior and add a regression case when existing coverage misses the issue. For wording edits, inspect the resulting text. Run required repository checks on the final changes using the project's entry points. Fix failures caused by your edits and rerun the affected checks. Related comments can share a check.
10. Before posting any replies, recheck every target against the final diff at its file and hunk or symbol. A later edit can supersede an earlier fix. Rerun affected tests and reply with the outcome that survived. For each verified item, call `record_comment_reply` with its ID and the `revision` returned by `get_comment_context` when present. Name the finding or fix, its location, and the actual test command and result when tested. If feedback changed, refresh it and verify the updated request before replying.
11. Leave affected comments pending when the target or intent remains unclear or a required check fails or cannot run. Continue with independent comments. In chat, recap every in-scope comment with its file and posted reply, or the specific blocker, including the failed command or missing prerequisite.
