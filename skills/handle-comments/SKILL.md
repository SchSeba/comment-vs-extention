# Handle Local Review comments

1. Find the absolute Git worktree root with `git rev-parse --show-toplevel`. If the user specifies a worktree, use that worktree. If the target is ambiguous, ask which worktree they mean.
2. Before fetching comments, read the review checkout's `AGENTS.md` and any coding, reviewing, and validation guidance in `.ai-rules/`. Identify the project by its canonical Git remote's repository name, or the worktree name if there is no remote. In an available [ai-plugins](https://github.com/SchSeba/ai-plugins) checkout, or a temporary clone of that repository, read the project's `CODING.md`, `REVIEWING.md`, and `VALIDATION.md` under `projects/<project>/` when present. Apply those conventions and checks, giving the review checkout's own instructions precedence. If shared guidance is unavailable, report that and use the checkout's guidance.
3. Call the `local-review` MCP server's `list_pending_comments` tool with that root as `repository` and the `scope` from the user's prompt if provided. If the tool is unavailable, tell the user to check `/mcp` and resume their session after configuring the server. If the result is empty, report that there are no pending comments on the current branch.
4. Work through comments on the same file in listed order. Call `get_comment_context` with the worktree root and that comment's ID just before addressing it, even if you already read the file for an earlier comment. Inspect the current file against the saved excerpt and nearby lines. Saved line numbers refer to the original snapshot. A changed range is an area to inspect. For ambiguous or missing anchors, act only when you can verify the target from the current code and the feedback.
5. Pass each pending item's `scope` to `get_comment_context` and `record_comment_reply`. Stop if the checkout or branch changed. For a follow-up, use the preceding feedback and summary returned by `get_comment_context`. Check whether earlier edits already satisfy the feedback. Verify that outcome or apply and verify the remaining fix while preserving existing edits. Record a short summary with the exact pending ID and the `revision` from `get_comment_context` when present. If the tool reports that the feedback changed, refresh it and verify the updated request before replying. Leave blocked comments pending.
6. Give the user one short line per comment with the file and the fix or blocker.
